## 3. Concept and hero story

**The product is an alert-driven investigator, not a chat box over a graph.** An anomaly fires, the agent investigates through graph tools, and the answer arrives with a path, an owner, a recommended action and a source for every claim. The company is fictional (**DashMart**), which keeps us inside rule 6 and gives us full control of the data.

What separates this from RAG over Slack and Jira:

1. **Proactive.** The investigation starts from an alert node, not a typed question.
2. **Provenance.** Every statement links to a node or edge, and the panel shows the source artifact (the message, ticket or SOP paragraph).
3. **Memory.** The finding is written back as typed memory and changes how the next similar incident is handled.
4. **Graph-dependent.** With graph tools off, the agent cannot answer the multi-hop cases (rule 3).

**Hero scenario A: the SLA drop in South Delhi.** All names and numbers are invented for the demo and labeled synthetic.

1. Alert: promise time at store SD-04 rose from 9.5 to 16 minutes in two hours.
2. The pick-time metric traces to a hero SKU, Probiotic Buttermilk, moved to a back freezer, 14 steps from packing.
3. The move traces to decision DEC-209, discussed in the store-ops Slack thread by the store manager, Vikram.
4. The reason: front chiller A1 is broken, and facilities ticket FAC-882 is unassigned.
5. A growth campaign, Summer Coolers, promoting that same SKU launched three hours ago under growth PM Ananya.
6. Output: the campaign is the amplifier, the chiller is the root cause. Recommended actions are to pause the campaign for that zone and assign FAC-882 to the facilities lead, Rajesh.

**Supporting scenario C: what breaks if a supplier is late.** A downstream traversal from supplier to dark stores to high-velocity SKUs to active campaigns to owners. It is almost pure graph work, so it is fast and cheap to demo.

**Backup scenario B: ghost inventory.** Refund spike on one SKU while the stock system shows units on hand, traced through a batch blocked by a shelf-life SOP and a stuck sync service to its last committer. Build it only if time remains after the decision gate.

**Honesty line for the demo:** say once, early, that the data is synthetic and that the graph structure, queries and agent are the real work.

## 4. Architecture

**FalkorDB is the only data store, and every layer of the product reads from it or writes to it.** That is the design answer to rule 3: there is no second database to fall back on, so removing the graph removes the product.

&#91;embedded content: architecture · 6 layers around FalkorDB, plus the proof harness\]

Data enters through the Ingestor, which validates before it writes. The Investigator reaches the graph only through the tool layer, so every step is a named query we can show and explain. The backend turns each tool result into an event, and the UI renders those events and nothing else.

How the architecture answers each requirement:

- **Rule 3 (graph does real work):** the Ingestor, the tools, the Investigator's memory and the UI's events all depend on FalkorDB. The proof harness demonstrates it.
- **Rule 6 (allowed data):** the only sources are the generator's output and pasted synthetic text.
- **Track 03:** one graph holds documents, tickets, chats, people, decisions and the evidence that links them, with provenance on every claim.
- **Track 02:** two agents coordinate through graph state, memory is typed and persistent, and each tenant has its own graph.
- **Track 01:** graph queries and algorithms are agent tools, selected over MCP, and the answer includes a recommended action.

## 5. Graph data model

The model has **10 core labels and 3 agent-layer labels**, and every relationship type must be used by at least one query in `queries/`. Any type no query touches gets deleted before submission, which keeps the model small enough to defend under rule 12.

**Core labels (the company):**

| Label | Key properties | Purpose |
| --- | --- | --- |
| Person | id, name, role, team | Owners, authors, experts |
| Store | id, name, zone | Dark stores |
| SKU | id, name, category, is\_hero | Products |
| Equipment | id, kind, location | Chillers, racks, scanners |
| Supplier | id, name | Inbound supply |
| Campaign | id, name, status, started\_at | Growth pushes |
| Ticket | id, key, title, status | Jira-style tickets |
| Decision | id, summary, decided\_at | Choices with a recorded reason |
| Artifact | id, kind (slack, sop, ticket\_text), text, ts, source\_ref | The raw evidence behind every claim |
| Alert | id, kind, metric, before, after, ts | Anomalies that start investigations |

**Agent-layer labels (the Brain):**

| Label | Purpose |
| --- | --- |
| Investigation | Shared state for one case; every step and finding hangs off it |
| Finding | One verified fact from one tool call, with edges to what it cites |
| Memory | Learned knowledge. Carries a second label: Episodic (what happened), Semantic (facts that hold), or Procedural (what to check first) |

**Relationship types:**

| Relationship | From to | Used for |
| --- | --- | --- |
| STOCKS | Store to SKU | Impact traversal |
| HAS\_EQUIPMENT | Store to Equipment | Locating faults |
| SUPPLIES | Supplier to SKU | Supplier-delay impact |
| PROMOTES | Campaign to SKU | Finding amplifiers |
| TARGETS | Campaign to Store | Scoping the pause action |
| OWNS | Person to Campaign, Ticket, Equipment or Supplier | Who owns what |
| WORKED\_ON | Person to Equipment, Ticket or SKU | Who knows what (expert query) |
| ABOUT | Ticket to Equipment | Linking faults to work |
| CHANGED | Decision to SKU (properties: from, to) | Tracing a move |
| MADE\_BY | Decision to Person | Decision owner |
| BECAUSE\_OF | Decision to Ticket or Equipment | Why it happened |
| EVIDENCE\_FOR | Artifact to Decision, Ticket, Campaign or Alert | Provenance |
| AUTHORED\_BY | Artifact to Person | Who said it |
| AT and INVOLVES | Alert to Store, Alert to SKU | Anchoring an alert |
| TRIGGERED\_BY and PART\_OF | Investigation to Alert, Finding to Investigation | Shared state |
| CITES and LEARNED\_FROM and ABOUT\_ENTITY | Finding to any node; Memory to Investigation; Memory to any node | Memory and proof |

**Per-tenant graphs.** Each tenant gets its own FalkorDB graph with the same schema: `dashmart` for the main demo and `freshloop`, a tiny second company, to show that memory never crosses tenants. All queries take the graph name from the request, never from a global.

**Indexes.** Full-text on Artifact.text, Ticket.title, SKU.name and Person.name, so anchor search runs inside FalkorDB. A vector index on Artifact embeddings is a stretch goal; confirm exact index syntax in the FalkorDB docs before writing it. Unique constraints on id properties keep `MERGE` safe when the live-event button ingests data.

## 6. Agent tools, Cypher and MCP

**The agent never writes free-form Cypher.** It chooses among parameterized tools whose queries we wrote and read line by line. This is the main source of reliability, and it is also the easiest way to satisfy rules 3 and 12: the queries are the product, and we can explain each one.

| Tool | What it does in FalkorDB | Track |
| --- | --- | --- |
| search\_artifacts | Full-text search over Artifact.text, Ticket.title, SKU.name to find anchor nodes | 03 |
| explore\_neighbors | One to two hop expansion around a node, filtered by relationship type | 03, 01 |
| trace\_decision | Follows CHANGED, MADE\_BY, BECAUSE\_OF and EVIDENCE\_FOR from an alert's SKU to the decision, its author, its cause and its source messages | 03 |
| find\_amplifiers | Active campaigns that PROMOTE the affected SKU and TARGET the affected store, with their owners | 03, 01 |
| find\_expert | Ranks people by WORKED\_ON edges to an entity, as in the example on the hackathon page | 03 |
| impact\_of | Downstream traversal from a supplier or equipment node to stores, SKUs, campaigns and owners | 01 |
| connect\_path | Shortest path between two nodes, so the agent can test whether two events are linked | 01 |
| rank\_people | A graph algorithm (PageRank or degree centrality) over the people subgraph for incident ownership | 01 |
| commit\_event | Validated ingestion of a new Slack message or ticket update into nodes and edges with MERGE | 03 |
| write\_memory and recall\_memory | Writes and reads typed Memory nodes (section 8) | 02 |

**Example queries to include in `queries/`** (parameters begin with `$`):

```cypher
// trace_decision: from an alert to the decision, its author, cause and evidence
MATCH (a:Alert {id: $alert_id})-[:INVOLVES]->(s:SKU)
MATCH (d:Decision)-[c:CHANGED]->(s)
OPTIONAL MATCH (d)-[:MADE_BY]->(p:Person)
OPTIONAL MATCH (d)-[:BECAUSE_OF]->(cause)
OPTIONAL MATCH (ev:Artifact)-[:EVIDENCE_FOR]->(d)
RETURN d, c.from AS moved_from, c.to AS moved_to, p, cause, collect(ev) AS evidence
```

```cypher
// find_amplifiers: active campaigns pushing the affected SKU into the affected store
MATCH (a:Alert {id: $alert_id})-[:AT]->(st:Store)
MATCH (a)-[:INVOLVES]->(s:SKU)
MATCH (cm:Campaign {status: 'active'})-[:PROMOTES]->(s)
MATCH (cm)-[:TARGETS]->(st)
OPTIONAL MATCH (o:Person)-[:OWNS]->(cm)
RETURN cm, o
```

```cypher
// impact_of (supplier): what a late supplier breaks, and who to tell
MATCH (sup:Supplier {id: $supplier_id})-[:SUPPLIES]->(s:SKU)<-[:STOCKS]-(st:Store)
OPTIONAL MATCH (cm:Campaign {status: 'active'})-[:PROMOTES]->(s)
OPTIONAL MATCH (o:Person)-[:OWNS]->(cm)
RETURN st.name AS store, s.name AS sku, cm.name AS campaign, o.name AS owner
```

```cypher
// find_expert: who has touched this entity the most
MATCH (p:Person)-[:WORKED_ON]->(x {id: $entity_id})
RETURN p.name AS person, count(*) AS touches
ORDER BY touches DESC LIMIT 5
```

These are drafts. Run each against real seed data and confirm the syntax against docs.falkordb.com/cypher and docs.falkordb.com/algorithms before relying on them, including the exact call syntax for the graph algorithms.

**Tool result contract.** Every tool returns `{result, touched: {nodes, edges}, sources: [artifact ids]}`. The `touched` ids drive the graph animation and the `sources` drive the provenance panel, so the UI needs no logic of its own and cannot show a path the agent did not take.

**MCP.** Wrap the tools in an MCP server over FalkorDB. The agent loop discovers and calls them through MCP, which is what Track 01 lists under tool selection. Build the plain function layer first, then add the MCP wrapper (about 2 hours), so the demo never depends on the wrapper.

**Answer validator.** The final answer is a structured object: each claim carries the Finding ids that support it. A claim with no Finding is dropped and logged. This is how we deliver "answers with clear sources" and avoid unsupported statements.

**Model.** Use any tool-calling LLM the team has an API key for; record the model name in the README. Keep temperature low and cap the loop at about 8 tool calls per investigation, with the Cypher tools doing the real work.

## 7. Synthetic data plan

**All data is generated by one deterministic script (`seed/generate.py`) with a fixed random seed,** so everyone gets the same graph and the demo never drifts. This satisfies rule 6 (synthetic data only) and makes the eval reproducible.

**Targets** (approximate; sized so the graph looks dense in the UI and still loads in seconds):

| Label | Count | Label | Count |
| --- | --- | --- | --- |
| Person | 30 | Ticket | 40 |
| Store | 6 | Decision | 25 |
| SKU | 60 | Artifact | 150 |
| Equipment | 24 | Alert | 10 |
| Supplier | 8 | Campaign | 12 |

That is about 365 nodes and several hundred edges. The second tenant (`freshloop`) is a small subset, around 40 nodes.

**Planted chains.** For each scenario the generator writes the full path with its evidence:

1. **Scenario A** (hero): alert, SKU, Decision DEC-209, Slack Artifact, Equipment fault, unassigned Ticket, and an active Campaign promoting the same SKU in the same store.
2. **Scenario C**: one supplier linked through SKUs to several stores and two active campaigns, with owners.
3. **Scenario B** (backup): a batch-block SOP Artifact, a sync-service ticket and its last committer.

**Distractors and negative controls.** Without these, any query looks smart:

- A second store with a rack move that did not cause an SLA drop.
- A campaign on a different SKU in the same store.
- A broken chiller whose ticket is already assigned and fixed.
- The same SKU name in two stores with different histories.
- Slack messages that mention the right words but belong to the wrong incident.

**Unstructured text.** The Slack, SOP and ticket text is written once (by an LLM, then reviewed and edited by a teammate), saved as JSON fixtures, and committed. The generator reads the fixtures; it does not call a model at seed time. Disclose this in the README AI section.

**Eval set.** Ten seeded incidents, each with a ground-truth root cause and owner, stored in `eval/incidents.json`. Scenario A is one of them. See section 10.

**Hygiene.**

- Names are invented and not matched to real people or companies.
- A visible "synthetic data" label sits in the UI footer and the README.
- No scraping, no real exports, nothing behind a login (rule 6).
- The generator and fixtures are committed so judges can reproduce the graph with one command.

## 8. Typed memory and coordination (Track 02 hooks)

**Memory must change a later investigation, or it does not count.** We build three memory types as graph nodes and prove the effect with a before-and-after run.

| Type | Node | Written when | Example | How it is used |
| --- | --- | --- | --- | --- |
| Episodic | Memory:Episodic | An investigation passes the answer validator | "Incident SD-04 on Oct 16: campaign amplified a chiller fault" | Recalled for similar alerts; linked to the Investigation and the entities involved |
| Semantic | Memory:Semantic | A fact is confirmed across steps or incidents | "Chiller A1 feeds the hero SKUs for SD-04" | Reduces search; carries a confidence and a last-confirmed date |
| Procedural | Memory:Procedural | A resolution pattern repeats | "SLA drop with a rack move: check active campaigns, then equipment tickets" | Read at the start of an investigation; reorders tool calls |

**Keeping knowledge current.** Semantic memories are never overwritten. A newer fact gets a SUPERSEDES edge to the old one, so the history stays traceable and stale facts stop being recalled. Every memory stores the Finding ids that justify it.

**Two agents coordinating through the graph.** This meets the shared-state focus without a four-agent system:

1. **Ingestor** reads new events (the live-event button), extracts nodes against the fixed schema, validates, and MERGEs them. It can create an Alert.
2. **Investigator** starts from an Alert, writes Findings under an Investigation, and writes memory at the end.

They share no code path except the graph, so the handoff is visible: Alert created by one, picked up by the other. If time allows after the decision gate, split the Investigator into department specialists that each write Findings to the same Investigation. Do not claim sub-agents if they are only tool groups.

**Persistent history.** The Investigation node stores the turns of its conversation, so a follow-up question reuses earlier Findings instead of re-querying.

**Proof runs (all measured, none estimated):**

- **Memory effect:** run the Scenario A alert on store SD-04, then a similar alert on another store with a procedural memory in place. Report the number of tool calls and seconds for each.
- **Tenant isolation:** an automated test that every query against `freshloop` returns nothing from `dashmart`.
- **Concurrency:** a small script runs about 20 parallel investigations against one instance and records p50 and p95 latency and the count of failed writes. Report the actual numbers, with the hardware stated.

**Cuts if behind:** drop the concurrency script first, then semantic memory, and keep episodic plus procedural plus the tenant test.

## 9. UI, streaming and provenance

**The UI only renders what the backend reports.** It holds no reasoning logic, so it cannot draw a path the agent did not take. This is the fix for the "visualization drawn over ordinary storage" failure in rule 3.

**Stack (recommended, change freely):** a Python backend (FastAPI) with the FalkorDB client and an SSE stream; a React frontend with `react-force-graph-2d`. Use 2D, because 3D looks good in a screenshot and stutters when the path animates.

**Screens and controls:**

| Element | Behavior | Why it matters |
| --- | --- | --- |
| Graph canvas | All nodes colored by label group; touched nodes and edges light up in sequence as tool results arrive | The first-glance wow, driven by real data |
| Agent hub | A visual node at the center, labeled as the agent. Edges to it appear only for nodes the agent actually queried | Matches the reference images without faking data. The hub is a UI element, not a graph node, and the README says so |
| Alert list | Click an alert to start an investigation | Shows the Brain is proactive |
| Step timeline | Each tool call, its arguments and its result size | Explainability for Track 01 |
| Answer panel | Claims with numbered citations; each citation is a Finding | Answers with clear sources |
| Provenance drawer | Click any node, edge or citation to see the source Artifact text, author and timestamp | Tracing decisions to source |
| Graph on or off switch | Disables the graph tools so the agent has only plain search | The rule 3 proof |
| Simulate event button | Pastes a Slack or ticket text, runs the Ingestor, and the new nodes pop into the canvas | Keeping knowledge current |
| Memory view | Shows the new Memory node wired to the Investigation | Track 02 proof |
| Tenant switcher | Switches between `dashmart` and `freshloop` | Isolation proof |
| Footer label | "Synthetic data" | Rule 6 transparency |

**Event stream (SSE).** One event type per step: `investigation_started`, `tool_call`, `nodes_touched`, `edges_touched`, `finding_written`, `answer_ready`, `memory_written`, `node_created`. Each carries ids that exist in FalkorDB.

**Recorded runs.** Save each investigation's event log as JSON. The UI can replay it for the demo video and as a fallback if the model API fails. A replay must be labeled "replay" in the UI, and the live path must still work on the deployed app.

**Performance guardrails.** Cap the visible graph near 400 nodes, precompute a stable layout so the canvas does not jitter, and animate along edges at a pace people can follow (about 400 to 600 ms per hop).

## 10. Proof: ablation, baseline and eval

**Three separate proofs, each aimed at a specific rule or track focus.** None of them uses numbers we have not measured.

**1. Graph dependency (rule 3).**

- **Dependency test:** a script stops the FalkorDB container and shows that the app cannot answer. The README states that there is no second data store behind the Brain.
- **Ablation switch:** with graph tools off, the agent keeps only a flat text search with no relationships. Run the Scenario A alert both ways on camera. The expected outcome is that the flat agent finds the Slack thread but cannot connect it to the campaign, the ticket or the owner. Run it for real before promising this in the video; if the flat agent succeeds, strengthen the distractors, not the narration.

**2. RAG baseline (comparison, not part of the product).** A plain retrieval pipeline (embedding or keyword search over the same Artifact text, top 5 chunks, same LLM, same question). Give it a fair setup: tune its prompt and chunking once, with the same effort spent on the graph agent, and record the exact configuration in `eval/README.md`. Rule 17 prohibits manipulating judging, and a rigged baseline would be exactly that.

**3. Small eval on 10 seeded incidents.** Ground truth lives in `eval/incidents.json`. Score each run on:

| Metric | How scored |
| --- | --- |
| Root cause correct | A teammate checks against ground truth |
| Owner correct | Exact match on the person node |
| Citations support the claims | Every cited Artifact is a required piece of evidence or a plausible supporting one |
| Tool calls and seconds | Logged automatically |
| Hallucinated entities | Entities in the answer that do not exist in the graph |

Report the results for the graph agent, the flat-search agent and the RAG baseline side by side, with n stated as 10. With ten cases the numbers are illustrative, not statistically significant, and the video and README should say so.

**Tests worth writing (and being able to explain):** a schema test that the generator produces the planted chains; a query test per tool against the seed; the tenant isolation test; the validator test that rejects a claim with no Finding; the ingestion test that a malformed extraction is rejected without changing the graph.

## 13. Risks, cut list and fallbacks

**The biggest risk is a polished UI over thin graph logic, which rule 3 treats as disqualifying.** Build the Cypher tools and the ablation before the interface.

| Risk | Early warning | Mitigation and fallback |
| --- | --- | --- |
| Graph reads as decoration (rule 3) | Flat-search agent solves Scenario A | Strengthen distractors; run the dependency test and ablation by Friday night |
| LLM tool loop is flaky | Wrong tool order, loops, malformed arguments | Parameterized tools, low temperature, loop cap, validator, labeled replay mode |
| FalkorDB or Cypher surprises | A query fails on real seed data | Test queries against the seed early; check docs.falkordb.com; ask in the Discord |
| Data too clean, so any approach works | RAG baseline matches the graph agent | Add negative controls and cross-incident noise |
| UI eats the schedule | Frontend still not showing real events on Saturday noon | 2D canvas, fixed event contract, cap node count, cut cosmetic work |
| Deployment fails | Live URL down on Saturday night | Deploy Friday; keep local setup instructions and the demo video complete, as rule 10 allows |
| Scope creep across three tracks | Any track missing proof at the gate | Apply the Saturday decision gate; name only tracks that work |
| Rule violation (data, AI disclosure, timing) | Any checklist item unchecked | Compliance matrix in section 2; final review Sunday 6 PM IST |
| API limits or cost | Rate-limit errors during demo prep | Cache outputs, record runs, keep a spare key |
| Rules or schedule updated | Discord announcement | Check the community channels at the start of each day |
| Fatigue | Mistakes after long stretches | Sleep blocks are scheduled; a rested demo beats a rushed feature |

**Cut list, in this order, if the schedule slips:**

1. Concurrency script
2. Scenario B
3. Vector index (keep full-text)
4. Splitting the Investigator into sub-agents
5. Semantic memory (keep episodic and procedural)
6. The Track 01 claim and MCP wrapper, if the MCP server is not stable by Saturday night
7. Tenant switcher in the UI (keep the isolation test)
8. Blog post, which is a side prize and comes last

**Never cut:** the dependency test, the ablation, the provenance panel, the README graph model and queries, the demo video, and the AI disclosure.
